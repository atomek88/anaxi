## TF.app-capture · iOS capture with creation strategies
> up: TF.intake · state: settled · links: submits→TF.intake-pipeline

The iOS app (Swift 6, SwiftUI, iOS 17+) offers three ways to create a task: a typed entry sheet, a
hold-to-record voice button, and a "do now" shortcut reachable from the home screen, a widget, and an App
Intent (Siri and Shortcuts). For new users the landing flow collects what the features need, in order:
sign-in ([[TF.auth]]), time zone and working hours, calendar connection ([[TF.calendar-access]]), and
optionally a phone number for SMS capture. Each step can be skipped except sign-in; skipped steps show up as
a setup card on the home screen.

#### D-TF-04 · Task creation uses the Strategy pattern
Each input mode is a `TaskCreationStrategy`: it collects input its own way and returns the same `TaskDraft`.
One `TaskSubmitter` takes any draft, persists it, and sends it. A new mode (share sheet, email forward) is a
new strategy; the submit path does not change, and neither does any other strategy.
Rejected: one view model per mode with its own submit code (three copies of retry and offline handling to
keep in sync); one view model with a `switch` over modes (every new mode edits shared code and its tests).

Offline: drafts are written to an on-device outbox before any network call and retried until the backend
acknowledges them, so a task typed in a tunnel is never lost. The durability promise of [[TF.intake]]
starts on the device, not at the queue.

Contract: [[TF.task-create-flow]]. Code: [[TF.task-create-swift]].

## TF.channel-gateway · SMS and voice entry points
> up: TF.intake · state: draft · links: submits→TF.intake-pipeline, records→TF.outcomes

Replaces the retired SMS-only node `TF.sms-gateway` (see `_tombstones.md`).

SMS: users text TaskFlow's long code. Inbound messages arrive on an SNS topic `sms-inbound`, which triggers
the `smsInbound` Lambda. It resolves the sender with one read of `PHONE#<E.164>` ([[TF.auth]]). Messages
from unbound numbers get the "link your number in the app" reply and are dropped. Replies of `done` or
`done <n>` (n = position in the morning summary) are outcome reports, not tasks, and go to
[[TF.outcomes]]. Everything else becomes a submission. Outbound SMS (confirmations, verification codes,
nudges) goes through the same provider behind one `SmsSender` port.

Voice: the app records AAC audio of at most 60 seconds, asks the API for a presigned S3 upload URL, uploads,
and calls the API to submit. Amazon Transcribe runs a batch job on the object; its completion event, routed
by an EventBridge rule, triggers `voiceTranscribed`, which reads the transcript and produces a submission
with `channel: "voice"` and the mean word confidence. Audio objects expire after 7 days by lifecycle rule.

#### D-TF-06 · Server-side speech-to-text
One transcription path for app recordings now and a phone-call channel later, with transcript and confidence
stored next to the rest of the submission.
Rejected: on-device `SFSpeechRecognizer` (no path for non-app channels, and quality and language support
vary by device and OS version).

- ⚑ Q-TF-02 · SMS provider: AWS End User Messaging two-way SMS (same account, delivery to SNS) or Twilio
  (faster number provisioning, webhook delivery)? Both need US 10DLC registration. Blocks the SMS half of
  this node and its contract.

## TF.intake-pipeline · Ordered queue and normalizer
> up: TF.intake · state: settled · links: feeds→TF.scheduler

Every entry point (`POST /v1/tasks` from the app, `smsInbound`, `voiceTranscribed`) writes one submission
envelope to the SQS FIFO queue `intake.fifo` and only then acknowledges the user. The `normalize` Lambda
consumes the queue in batches of up to ten, parses each envelope into a task, writes it to DynamoDB, sends
the confirmation, and for "do now" tasks invokes the planner for that user directly. Failed messages retry
three times and then move to `intake-dlq.fifo`, which alarms when it is not empty.

#### D-TF-05 · SQS FIFO with one message group per user
`MessageGroupId = userId` keeps one user's submissions in order while different users are processed in
parallel. `MessageDeduplicationId = submissionId`, generated by the client, makes retries from the app or
the SMS provider idempotent within the five-minute deduplication window; the DynamoDB write is conditional
on the task not existing, which covers retries after the window.
Rejected: an EventBridge bus (no per-user ordering, no buffering while the consumer is failing); Kinesis
Data Streams (shard management for a few thousand messages a day).

Contract: [[TF.submission-envelope]]. Code: [[TF.normalizer-lambda]].

## TF.task-create-flow · Creation strategies, outbox, and task API contract
> up: TF.app-capture · kind: contract · state: settled · decided-by: D-TF-03, D-TF-04, D-TF-05 · links: calls→TF.submission-envelope, authenticates-with→TF.auth

### Draft model
Every strategy returns a `TaskDraft`. Fields map one-to-one onto the request bodies below, except
`localAudioPath`, which never leaves the device.

| Field | Type | Required | Set by |
|---|---|---|---|
| `submissionId` | UUID v4, lowercase | yes | strategy, once; reused on every retry |
| `text` | string, 0–500 chars | yes | typed or do-now text; empty for voice |
| `title` | string, ≤ 120 chars | no | typed entry only; the server derives it otherwise |
| `durationMinutes` | int, 5–480 | no | typed entry picker; do-now sends 25 |
| `deadline` | ISO 8601 date-time | no | typed entry date picker |
| `doNow` | bool | yes | true only from the do-now strategy |
| `channel` | `app` or `voice` | yes | strategy |
| `localAudioPath` | file path | voice only | voice strategy; device only |
| `audioUploadId` | string | voice only | submitter, after upload |

### Strategy contract
```swift
protocol TaskCreationStrategy: Sendable {
    var mode: CreationMode { get }                      // .typed, .voice, .doNow
    func makeDraft(context: CreationContext) async throws -> TaskDraft
}
```
A strategy owns its input UI and validation, and either returns a complete draft or throws
`CreationError.cancelled` or `CreationError.invalid(reason)`. Strategies never touch the network or the
outbox. The voice strategy returns a draft pointing at a local audio file; uploading it is the submitter's
job, so a recording made offline is as durable as typed text.

| Strategy | Entry points | Draft rules |
|---|---|---|
| `TypedEntryStrategy` | "+" button, share sheet | trims text; 1–500 chars; deadline must be in the future |
| `VoiceStrategy` | hold-to-record button | 1–60 s of audio; `channel: voice`; empty `text` |
| `DoNowStrategy` | widget, App Intent, long-press on app icon | text from the intent or a one-line prompt; `doNow: true`; 25 min |

### Outbox states
`TaskSubmitter` writes every draft to the outbox first, then drives it through these states:

| From | Event | To |
|---|---|---|
| `saved` | send starts | `sending` |
| `sending` | 202 from the API, or 409 on a voice submit (an earlier attempt already got through) | `acknowledged` |
| `sending` | network error, 429, 5xx | `retryWait`: 2 s, doubling, capped at 5 min; resumed by a background task |
| `sending` | 404 on a voice submit (upload expired after 24 h) | `retryWait` with `audioUploadId` cleared, so the audio is uploaded again |
| `sending` | 400, 409, 422 | `rejected`: shown with the server message, kept for editing |
| `sending` | 401 after one forced token refresh | `needsSignIn`: resumes after sign-in |

#### D-TF-09 · On-device outbox in SwiftData
Drafts live in a SwiftData `OutboxItem` store until acknowledged, and the same `submissionId` is sent on
every retry so the queue deduplicates ([[D-TF-05]]).
Rejected: in-memory retry (tasks lost when the app is killed); `URLSession` background transfers for JSON
calls (no per-item state for the UI, and awkward with token refresh).

### API contract
Base URL `https://api.taskflow.app`. Every call sends `Authorization: Bearer <access token>` ([[TF.auth]]).

| Method and path | Body | Success | Errors |
|---|---|---|---|
| `POST /v1/tasks` | the draft without `localAudioPath` and `audioUploadId` | `202 {submissionId, status: "queued"}` | 400 invalid, 401, 409 same `submissionId` with a different body, 429 |
| `POST /v1/voice-uploads` | none | `201 {audioUploadId, uploadUrl, expiresAt}`; URL valid 15 min, upload kept 24 h | 401, 429 |
| `PUT <uploadUrl>` | audio bytes, `Content-Type: audio/mp4` | `200` from S3 | 403 when the URL expired: request a new one |
| `POST /v1/voice-uploads/{audioUploadId}/submit` | `{submissionId, doNow}` | `202 {submissionId, status: "transcribing"}` | 404 unknown or expired upload, 409 already submitted |

A replay of `POST /v1/tasks` with an identical body returns `202` again. A `202` means the envelope is in
`intake.fifo` ([[TF.submission-envelope]]); the app says "Got it" at that point, never "Scheduled".
Placement reaches the user later as a push ([[TF.notifications]]).

## TF.submission-envelope · Envelope, normalization rules, and task record
> up: TF.intake-pipeline · kind: contract · state: settled · decided-by: D-TF-02, D-TF-05, D-TF-06 · links: triggers→TF.placement

### Envelope v1
Every producer sends exactly this JSON as the SQS message body, with `MessageGroupId = userId` and
`MessageDeduplicationId = submissionId`.

```json
{
  "v": 1,
  "submissionId": "4d1c8f0e-6a8e-4c62-9b8e-2f3f8a1d7c55",
  "userId": "3b1e5c2a-91f4-4d7e-a0c2-5f8d6e2b9a10",
  "channel": "sms",
  "receivedAt": "2026-10-07T18:02:11-05:00",
  "text": "now: call the bank 15 min",
  "hints": { "doNow": false },
  "sourceConfidence": 1.0,
  "replyTo": "+15125550142",
  "correlationId": "c-7f3a9e"
}
```

| Producer | Trigger | What it sets |
|---|---|---|
| `submitTask` | `POST /v1/tasks` | `channel: app`; `hints` from the body; `sourceConfidence: 1.0`; `userId` from the JWT `sub` |
| `voiceTranscribed` | Transcribe job state change → EventBridge rule | `channel: voice`; `text` = transcript; `sourceConfidence` = mean word confidence; `hints.doNow` from the submit call |
| `smsInbound` | SNS topic `sms-inbound` | `channel: sms`; `replyTo` = sender; `userId` from `PHONE#<E.164>` |

### Normalization rules, applied in order
1. Collapse whitespace and trim. Empty text and no `hints.title`: no task is created, and the user is told
   ("I couldn't hear a task in that") on the submission's channel.
2. "Do now": `hints.doNow`, or the text starts with `now:` or `asap:` (any case), which is then stripped.
3. Duration: `hints.durationMinutes`, else the first `<number> <m|min|minutes|h|hr|hours>` phrase, else "half
   an hour" (30) or "an hour" (60), else 30. The phrase is removed from the text. Clamp to 5–480.
4. Deadline: `hints.deadline`, else the first date phrase, read in the user's time zone. Past dates are
   ignored. With no stated time the deadline is 23:59 local that day. If the day itself is uncertain ("next
   week"), parse confidence is 0.7. The phrase and a dangling "by", "before" or "on" are removed.
5. Title: `hints.title`, else what is left of the text, sentence-cased, at most 120 characters.
6. Confidence = `sourceConfidence` × parse confidence. Below 0.6 the task gets `needsReview: true`.

#### D-TF-08 · Keep low-confidence tasks and flag them for review
A rejected submission makes the user retry through the same channel that just failed; a kept task with a
review flag costs one tap to fix and is placed meanwhile.
Rejected: rejecting below the threshold; asking a clarifying question synchronously (an SMS round trip
would hold up that user's message group in the FIFO queue).

### Task record
`PK = USER#<userId>`, `SK = TASK#<submissionId>`: the task ID is the submission ID, so a replay after the
five-minute deduplication window hits the conditional put (`attribute_not_exists(PK)`) and is a no-op.
Attributes: `title`, `durationMinutes`, `deadline?`, `doNow`, `needsReview`, `confidence`, `channel`,
`sourceText`, `status: "pending"`, `createdAt`.

### Delivery semantics
- Batch of up to 10, partial batch responses on. Because the queue is FIFO, the first failing message and
  every message after it in the batch are reported as failed, so no user's later submission overtakes an
  earlier one.
- `maxReceiveCount` 3, then `intake-dlq.fifo`. A malformed envelope takes the same path; there is one
  failure path, not two.
- Confirmations are sent only when the task was newly written: SMS reply "Added: <title> (<n> min<, by
  <day>>)" for `sms`, push for `voice`, nothing for `app` (it already showed "Got it").
- "Do now": after the write, invoke the planner asynchronously with `{trigger: "doNow", userId, taskId}`
  ([[TF.placement]]).
